# CameraSmart — سامانه تشخیص اشیا و حرکت در دوربین‌های مداربسته

سامانه‌ای کامل، آفلاین‌پذیر و پایدار برای پایش دوربین‌های RTSP: تشخیص اشیا با
**RF-DETR**، تشخیص حرکت، ردیابی اشیا، ثبت رویداد، هشداردهی (صدا + اعلان درون‌برنامه‌ای)،
گالری اشیای ذخیره‌شده (کامل + برش‌خورده)، ابزار رسم نواحی و خط عبور، جست‌وجوی مکانی،
نقشه حرارتی، پایش سلامت دوربین و مدیر GPU — همراه با رابط کاربری مدرن فارسی/راست‌به‌چپ
با **تقویم شمسی**.

```
┌──────────────┐   RTSP    ┌────────────────────────────┐   REST/WS   ┌───────────────┐
│  دوربین‌ها   │ ────────► │  Backend (FastAPI + ffmpeg)│ ──────────► │  React UI     │
└──────────────┘           │  motion → RF-DETR → tracker│  /api/ws    │  تقویم شمسی   │
                           │  → events/alerts → SQLite  │ ◄────────── │  گالری/نقشه   │
                           └────────────────────────────┘             └───────────────┘
```

## ۱. فهرست قابلیت‌ها (نگاشت به نیازها)

| نیاز | پیاده‌سازی |
|---|---|
| تشخیص اشیا با rf-detr | `app/services/detector.py` — پوشش تنبل روی ۵ وزن RF-DETR (nano…large)، رجیستری مدل مشترک بین دوربین‌ها |
| ورودی RTSP | `app/services/stream.py` — فرآیند ffmpeg برای هر دوربین (OpenCV فقط پشتیبان) |
| چند دوربین | `app/services/camera_manager.py` — یک worker مستقل و چرخه بازاتصال برای هر دوربین |
| ذخیره دسته‌بندی‌شده روی فایل‌سیستم + لاگ در دیتابیس | `services/storage.py` + `services/persistence.py` |
| مشاهده کامل و کراپ‌شده | گالری «اشیای ثبت‌شده» و صفحه اختصاصی شیء — هر دو تصویر کنار هم |
| پخش خام پیش‌فرض + علامت‌گذاری اختیاری | دکمه چشم روی هر دوربین؛ `?overlay=true` روی استریم MJPEG |
| بخش ویژه رویدادها | صفحه «رویدادها» + `GET /api/events` با فیلترهای کامل |
| ابزار رسم نواحی پردازش | `components/ZoneEditor.tsx` → نواحی `region` / `ignore` |
| شیء ثابت → یک تصویر با کیفیت‌ترین | Frame Quality Score در `services/quality.py` + حذف تکرار در `persistence.py` |
| ورود/خروج از کادر → تصویر + رویداد | رویدادهای `enter` / `exit` با تصویر اختصاصی |
| حساسیت هر دوربین (نوع/ابعاد/حرکت) | `class_config` هر دوربین (threshold، min_width، min_height، min_motion) |
| مدل/وزن و آستانه هر کلاس | انتخاب مدل به‌ازای هر دوربین + جدول قواعد کلاس‌ها |
| آمار ثبت اشیا | صفحه «آمار» + `GET /api/stats/overview` |
| تقویم شمسی | `backend/app/core/timeutil.py` و `frontend/src/lib/jalali.ts` (الگوریتم یکسان) |
| ذخیره جهت حرکت | ۹ جهت (`left/right/up/down` + چهار قطر + `stationary`) در `TrackRecord` |
| جست‌وجوی مکانی | صفحه «جست‌وجوی مکانی» — دوربین + رسم ناحیه + تاریخ/ساعت + نوع + جهت (+ خروجی CSV) |
| تشخیص عبور از خط | ناحیه نوع `line` (تریپ‌وایر) و رویداد `line_cross` |
| هشدار با زمان و ناحیه + صدا | `services/alerts.py` + صفحه «هشدارها» (صدا به‌صورت محلی در مرورگر تولید می‌شود) |
| نقشه حرارتی هر دوربین | `services/heatmap.py` + صفحه «آمار و نقشه حرارتی» |
| وضعیت دوربین | متصل / در حال اتصال / آفلاین / خطا / غیرفعال |
| سلامت دوربین (FPS، Bitrate، Resolution، Latency، Reconnect، Last Frame) | تب «سلامت دوربین» + `GET /api/cameras/{id}/health` |
| طراحی UTC در پایگاه داده، محلی در UI | TypeDecorator در `models/base.py` + تبدیل در `core/timeutil.py` |
| GPU Manager روی داشبورد | `services/gpu.py` (nvidia-smi/NVML/psutil): VRAM، اشغال، دما، FPS تشخیص، دوربین‌های فعال |
| مدل مشترک تا حد امکان | `DetectorRegistry` یک نمونه از هر مدل را بین همه دوربین‌ها به اشتراک می‌گذارد |

## ۲. پیش‌نیازها

- ویندوز ۶۴ بیتی (روی لینوکس هم اجرا می‌شود)
- **Python 3.11**
- **Node.js 20+** (فقط برای ساخت رابط کاربری)
- **FFmpeg 6+** شامل `ffmpeg` و `ffprobe` در PATH (مدیریت استریم به عهده آن است)
- کارت گرافیک NVIDIA با درایور ≥ ۵۲۵ (برای اجرای GPU؛ در غیر این صورت `CAMERASMART_DEVICE=cpu`)
- پایگاه داده: SQLite به‌صورت پیش‌فرض (بدون نصب) — PostgreSQL اختیاری

در این ماشین تست‌شده: Python 3.11.4، Node 24، FFmpeg 7.1، درایور ۵۹۲.۲۷ (CUDA 13.1)،
GPU: `NVIDIA GeForce GTX 1650 (4 GB)`.

> روی کارت گرافیک ۴ گیگابایتی مدل‌های `rf-detr-nano` یا `rf-detr-small` و نرخ تشخیص
> حدود ۵ فریم بر ثانیه پیشنهاد می‌شود؛ مدل `rf-detr-large` برای چنین GPU مناسب نیست.

## ۳. نصب و اجرا (متصل به اینترنت)

```powershell
# ۱) بک‌اند
cd backend
py -3.11 -m venv .venv
.venv\Scripts\python -m pip install --upgrade pip
.venv\Scripts\python -m pip install -r requirements-core.txt      # حداقلی
.venv\Scripts\python -m pip install -r requirements-ai.txt `
    --extra-index-url https://download.pytorch.org/whl/cu124      # هوش مصنوعی + CUDA

# ۲) پایگاه داده
.venv\Scripts\python -m alembic upgrade head
Copy-Item .env.example .env        # و در صورت نیاز ویرایش کنید

# ۳) رابط کاربری
cd ..\frontend
npm ci
npm run build                      # خروجی در frontend\dist

# ۴) اجرا (سرور هم API و هم رابط کاربری را سرو می‌کند)
cd ..\backend
.venv\Scripts\python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

> **اولین اجرا:** صفحهٔ «تعیین رمز ادمین» باز می‌شود؛ رمز را **دو بار** وارد کنید. از آن پس
> هر ورود همین رمز را می‌خواهد. حساب کاربری جداگانه‌ای وجود ندارد (سامانه تک‌کاربره است) و
> رمز فقط به‌صورت هش `scrypt` در پایگاه داده ذخیره می‌شود. تغییر رمز از **تنظیمات → امنیت و رمز
> ادمین** انجام می‌شود و همهٔ نشست‌های دیگر را می‌بندد.

سپس در مرورگر: **http://127.0.0.1:8000** — همان آدرس، رابط کاربری را نشان می‌دهد (و اگر
`frontend\dist` ساخته نشده باشد، در همان آدرس یک پاسخ JSON کوتاه درباره سامانه می‌بینید).
مستندات API: `http://127.0.0.1:8000/api/docs` — مشخصات سامانه به‌صورت JSON: `http://127.0.0.1:8000/api/info`

> نکته: اگر پورت را تغییر دادید (مثلاً `--port 8998`) همان پورت را در مرورگر باز کنید.
> برای توسعه رابط کاربری، پروکسی Vite به‌صورت پیش‌فرض به `127.0.0.1:8000` می‌رود؛ در صورت تغییر پورت،
> `VITE_BACKEND=http://127.0.0.1:8998` را قبل از `npm run dev` تنظیم کنید.

حالت توسعه رابط کاربری (با hot reload و پروکسی به بک‌اند):

```powershell
cd frontend
npm run dev            # http://127.0.0.1:5173
```

## ۴. نصب و اجرا

سه گام جدا وجود دارد: **دانلود** پیش‌نیازها، **نصب**، و **اجرا**. هر دستور فقط کار خودش را
می‌کند؛ نصب هیچ‌وقت اینترنت را لمس نمی‌کند و اجرا هیچ‌وقت چیزی نصب نمی‌کند.

سورس برنامه سر جای خودش (همین مخزن) می‌ماند. پوشهٔ `offline/` فقط چیزهایی است که باید
دانلود یا ساخته شوند: wheel های پایتون، وزن مدل، `ffmpeg`/`ffprobe` و رابط کاربری ساخته‌شده.

### گام ۱ — دانلود پیش‌نیازها (روی سیستمی که اینترنت دارد)

```powershell
powershell -ExecutionPolicy Bypass -File scripts\download_offline.ps1
# اختیاری:
#   -OutDir D:\offline                 محل دیگر برای بسته
#   -CudaTag cu124 | cu121 | cpu        (پیش‌فرض cu124، تأییدشده)
#   -Models small,base | nano,small,base
#   -ModelsFrom D:\roboflow-models     پوشه‌ای که rf-detr-*.pth در آن است
#   -FrontendDist path                  dist ساخته‌شدهٔ رابط کاربری (پیش‌فرض frontend\dist)
#   -DryRun                             فقط بررسی دسترسی منابع و حجم
#   -IndexUrl https://mirror/simple      میرور PyPI دیگر
#   -PipRetries 8                        تلاش دوبارهٔ pip در صورت قطع اتصال
#   -UseSystemProxy                      استفاده از پروکسی سیستم حتی اگر لوکال باشد
#   -WheelCache D:\wheel-cache          محل کش wheel ها (پیش‌فرض: %LOCALAPPDATA%\CameraSmart\wheel-cache)
#   -RefreshWheels                       نادیده‌گرفتن کش و دانلود دوباره
#   -NoWheelCache                       غیرفعال‌کردن کش
```

نکته‌ها:
- wheel ها برای **Python 3.11 / win_amd64 (cp311)** دانلود می‌شوند، حتی اگر خود اسکریپت با
  پایتون دیگری اجرا شود. نسخه‌ها از `backend\constraints.txt` خوانده می‌شوند.
- `torch`/`torchvision` جدا و با `curl -C -` دریافت می‌شوند تا یک قطعی وسط فایل ۲٫۴ گیگابایتی،
  دانلود را از صفر شروع نکند. اجرای دوبارهٔ اسکریپت، فایل‌های موجود را دوباره نمی‌گیرد.
- اگر dist رابط کاربری وجود نداشته باشد، اول در `frontend` دستورهای `npm ci` و `npm run build`
  را اجرا کنید (Node فقط همین‌جا لازم است، نه روی ماشین مقصد).
- اگر شبکه‌تان دانلود وزن مدل را مسدود می‌کند، فایل‌ها را از سیستم دیگری با `-ModelsFrom` بدهید؛
  MD5 بررسی می‌شود.

### گام ۲ — نصب (روی همان سیستم یا روی سیستم آفلاین)

```powershell
powershell -ExecutionPolicy Bypass -File scripts\install_offline.ps1
# اختیاری:
#   -BundleDir D:\offline     مسیر دیگر بسته
#   -Port 8080                 پورت ذخیره‌شده در .env
#   -DataDir D:\CameraSmartData  پوشهٔ داده بیرون از پوشهٔ برنامه (پیشنهادی برای بروزرسانی)
#   -Lan                       گوش‌دادن روی 0.0.0.0 + قانون فایروال (Administrator)
#   -Autostart                 اجرای خودکار در ورود کاربر (Administrator)
#   -Repair                    نصب دوبارهٔ بسته‌ها حتی اگر نصب باشند
```

این اسکریپت:
1. بسته را بازبینی می‌کند و اگر ناقص باشد با پیام روشن متوقف می‌شود (چیزی دانلود نمی‌کند)،
2. Python 3.11 را پیدا می‌کند و فقط اگر لازم باشد `backend\.venv` را می‌سازد،
3. نسخه‌های نصب‌شده را با فهرست پین‌شده مقایسه می‌کند؛ **اگر همه نصب باشند pip اجرا نمی‌شود**،
   وگرنه فقط کمبودها را با `--no-index --find-links offline\wheels` نصب می‌کند،
4. وزن مدل‌ها را در `backend\data\models`، `ffmpeg`/`ffprobe` را در `backendin` و رابط
   کاربری را در `frontend\dist` می‌گذارد — هرکدام فقط اگر نباشند یا فرق کنند،
5. `backend\.env` را فقط اگر نبود می‌سازد (فایل موجود دست‌نخورده می‌ماند)،
6. پایگاه داده را با Alembic به‌روز می‌کند و در پایان نسخه‌ها و `import` ها را بررسی می‌کند.

اجرای دوبارهٔ این دستور بی‌خطر است: همه‌چیز را بررسی می‌کند و چیزی را که نصب است دوباره نصب نمی‌کند.

### گام ۳ — اجرا

```powershell
powershell -ExecutionPolicy Bypass -File scripts
un.ps1
# اختیاری:
#   -Port 8080        پورت دیگر (پیش‌فرض: CAMERASMART_PORT در .env یا 8000)
#   -HostAddr ...     آدرس گوش‌دادن
#   -Lan              در دسترس بودن از شبکه
#   -Reload           حالت توسعه (بارگذاری دوباره با هر تغییر)
#   -OpenBrowser      باز کردن مرورگر پس از شروع
```

سپس در مرورگر `http://127.0.0.1:8000` را باز کنید و در اولین بازدید رمز ادمین را دو بار تعیین کنید.
برای توقف سرور `Ctrl+C`.

### بروزرسانی نسخه‌دار (بدون Git و بدون Node روی مقصد)

```powershell
# روی سیستم آنلاین: ساخت بستهٔ نسخه‌دار
powershell -ExecutionPolicy Bypass -File scripts\make_release.ps1
#   -Version 1.0.20261120    نسخهٔ دلخواه (پیش‌فرض: 1.0.<تاریخ امروز>)
#   -CodeOnly                فقط کد + رابط کاربری ساخته‌شده (چند ده مگابایت، پیش‌نیازها همراهش نیست)
#   -Flat                    محتویات در ریشهٔ zip (برای بروزرسانی یک نصب موجود)
#   -BuildFrontend           اجرای npm ci / npm run build حتی اگر dist باشد
#   -NoZip                   فقط پوشهٔ نسخه ساخته شود
```

**بروزرسانی یک نصب آفلاین موجود** (کمهزینه‌ترین راه؛ پیش‌نیازها دست‌نخورده می‌مانند):

```powershell
# روی سیستم آنلاین
powershell -ExecutionPolicy Bypass -File scripts\make_release.ps1 -CodeOnly -Flat
# روی سیستم مقصد: فایل CameraSmart-<version>-update.zip را داخل همان پوشهٔ برنامه
# «Extract Here» کنید (نه در پوشهٔ جدید)، سپس:
powershell -ExecutionPolicy Bypass -File scripts\install_offline.ps1
powershell -ExecutionPolicy Bypass -File scripts\run.ps1
```

`-Flat` پوشهٔ تو در تو نمی‌سازد و بستهٔ `-CodeOnly` حتی بدون wheel هم فهرست پین‌ها
(`offline\requirements-offline.txt`، `constraints-offline.txt`، `manifest.json`) را با خود می‌برد،
پس نصب‌کننده پین‌های قدیمی را از دست نمی‌دهد. هیچ چیزی از اینترنت یا از بستهٔ ۳٫۶ گیگابایتی
دوباره دانلود نمی‌شود.

خروجی در `release/CameraSmart-<version>/` (و یک zip) است: کد برنامه بدون `.venv`/`data`/`.env`،
رابط کاربری ساخته‌شده، اسکریپت‌ها، به‌همراه `version.json` (نسخهٔ برنامه، کامیت، نسخهٔ پایگاه‌داده).
روی سیستم مقصد فقط zip را باز کنید و همان دو دستور نصب/اجرا را بزنید؛ **نسخهٔ پایگاه‌داده** در
`version.json` با `alembic_version` مقایسه می‌شود و در صورت ناسازگاری نصب با پیام روشن متوقف می‌شود.

### کش wheel ها بین نسخه‌ها

دانلود دوبارهٔ حدود ۳٫۴ گیگابایت wheel برای هر بروزرسانی لازم نیست. `download_offline.ps1` یک کش
در `%LOCALAPPDATA%\CameraSmart\wheel-cache` نگه می‌دارد و از یک امضای SHA-256 روی فهرست پین‌ها،
برچسب CUDA و آدرس ایندکس استفاده می‌کند:

- اگر امضا تغییر نکرده باشد، **کل مرحلهٔ دانلود (شامل torch) رد می‌شود** و wheel ها از کش کپی می‌شوند.
- اگر فقط چند پین عوض شده باشد، امضا فرق می‌کند و دانلود انجام می‌شود؛ سپس کش به‌روز می‌شود.
- `-RefreshWheels` برای اجبار به دانلود دوباره، `-NoWheelCache` برای غیرفعال‌کردن، و
  `-WheelCache <path>` برای نگه‌داشتن کش روی درایو دیگر (مثلاً برای انتقال با فلش).

### جدا کردن داده از برنامه

با `install_offline.ps1 -DataDir D:\CameraSmartData` خط `CAMERASMART_DATA_DIR` در `backend\.env`
نوشته می‌شود (پایگاه‌داده، تصاویر ذخیره‌شده و وزن مدل‌ها به آنجا می‌روند). آن‌گاه بروزرسانی فقط
فایل‌های برنامه را عوض می‌کند و داده دست‌نخورده می‌ماند.

## ۵. ماتریس نسخه‌ها (سازگاری تضمین‌شده)

## ۶. قرارداد زمان (UTC در پایگاه داده، محلی در رابط کاربری)

- همه زمان‌ها در پایگاه داده **UTC aware** ذخیره می‌شوند (`UTCDateTime` TypeDecorator).
- نمایش در UI با منطقه زمانی `CAMERASMART_TIMEZONE` (پیش‌فرض `Asia/Tehran`) و تقویم شمسی.
- پارامترهای `start` / `end` در API می‌توانند ISO با `Z`/آفست یا محلی باشند
  (`core/timeutil.parse_dt`).
- تقویم شمسی در بک‌اند (`core/timeutil.py`) و فرانت‌اند (`lib/jalali.ts`) با **همان الگوریتم**
  پیاده‌سازی شده تا هرگز اختلاف نداشته باشند.
- پایان‌های روز شمسی برای جست‌وجو: `GET /api/system/day-bounds?jalali=1405/07/14`
  و در فرانت‌اند `jalaliDayBounds()`.

## ۷. معماری بک‌اند

```
app/
├── core/      config، timeutil (UTC+شمسی)، database، logging، media
├── models/    Camera/Zone، TrackRecord/ObjectImage/Event، Alert/HealthMetric/Setting
├── schemas/   Pydantic v2 (اعتبارسنجی نرمال‌شده نواحی، جهت‌ها، بازه زمانی)
├── services/  stream · detector · tracker · motion · quality · pipeline · persistence
│              storage · alerts · heatmap · search · stats · gpu · camera_manager
└── api/       cameras · objects · events · alerts · search · stats · system · ws
```

نکات کلیدی پیاده‌سازی:

- **pipeline.py** کاملاً مستقل از پایگاه داده است (ورودی فریم، خروجی نتیجه) و همین باعث
  تست‌پذیری بالای موتور تشخیص شده است.
- **persistence.py** بهترین فریم را با *Frame Quality Score* (تیزی/بلور، اندازه کادر،
  اطمینان، روشنایی) انتخاب و برای اشیای ثابت فقط یک تصویر نگه می‌دارد.
- **stream.py** هر دوربین را با یک فرآیند ffmpeg مدیریت می‌کند: چرخه بازاتصال با
  backoff، اندازه‌گیری FPS/تأخیر/لرزش/بیت‌ریت و دو حالت «تصویر خام» و «لایه تشخیص».
- **bus.py** رویدادها را با `call_soon_threadsafe` از thread های کاری به WebSocket می‌رساند
  (همراه با حلقه تاریخچه برای کلاینت تازه‌وصل).
- سرو کردن رابط کاربری: اگر `frontend/dist` وجود داشته باشد، همان سرور FastAPI آن را
  به‌صورت SPA سرو می‌کند (مسیرهای `/api` و `/media` هرگز با fallback پوشانده نمی‌شوند).

## ۱۱. وضعیت فعلی و محدودیت‌های شناخته‌شده

- **استنتاج واقعی RF-DETR روی GPU آزمایش شده است.** وزن‌ها (`rf-detr-base.pth` و
  هم‌خانواده‌ها) در کش خود کتابخانه `rfdetr` قرار می‌گیرند
  (`%USERPROFILE%\.roboflow\models`)، نه در `backend\data\models`؛ سامانه از همان کش
  استفاده می‌کند. در آزمایش این نسخه روی `GTX 1650` با یک ویدیوی ۶۴۰×۳۶۰ ساخته‌شده از
  یک تصویر واقعی: نرخ تشخیص ~۴.۳ فریم/ثانیه، مصرف VRAM ~۴۸۰ مگابایت، بار GPU ~۷۰٪، و
  ثبت واقعی اشیا (برچسب‌های مدل) به‌همراه رویداد ورود/خروج، جهت حرکت، دسته‌بندی فایل تصاویر
  و نقشه حرارتی صحت‌سنجی شد.
  نکته: در نبود وزن‌ها (مثلاً روی ماشین آفلاین پیش از اجرای اسکریپت دانلود) سامانه با شکست
  نرم کار می‌کند و پخش زنده، snapshot و ثبت رویداد ادامه می‌یابد.
- برای استفاده از فایل وزن محلی (`backend\data\models\rf-detr-*.pth`) باید فیلد
  `model_weights` همان دوربین پر شود؛ در غیر این صورت کتابخانه از کش پیش‌فرض خود
  استفاده می‌کند (رفتار پیش‌فرض و مورد آزمایش این نسخه).

  در این حالت هیچ‌چیز الکی گزارش نمی‌شود: اگر برای دوربینی «تشخیص» فعال باشد ولی موتور
  بارگذاری نشده باشد، به‌جای ساختن یک تشخیص بی‌فایده،
  `detection_fps` صفر می‌ماند، در «مدیریت GPU» شمارنده «دوربین‌های فعال» صفر است و دلیل
  دقیق خطا در فیلد `detector_error` (و به‌صورت هشدار زرد در فهرست دوربین‌ها و صفحه دوربین)
  نمایش داده می‌شود؛ مثلاً `ModuleNotFoundError: No module named 'rfdetr'`.
  هر دوربینی هم فقط یک بار تلاش برای بارگذاری می‌کند (نه برای هر فریم).
- ستون «بیت‌ریت» در پایش سلامت، اگر محفظه نرخ واقعی را گزارش نکند (وضعیت رایج در RTSP)،
  به‌صورت تخمینی از نرخ داده تصویر محاسبه می‌شود.
- نگه‌داری به‌صورت خودکار زمان‌بندی می‌شود (`CAMERASMART_RETENTION_AUTO_RUN=true`): اولین
  اجرا ۵ دقیقه پس از راه‌اندازی و سپس هر `CAMERASMART_RETENTION_INTERVAL_HOURS` ساعت؛
  تصاویر، رویدادها، هشدارها، معیارهای سلامت و سلول‌های نقشه حرارتی قدیمی‌تر از
  `CAMERASMART_RETENTION_DAYS` حذف می‌شوند. اجرای دستی: دکمه «اجرای پاک‌سازی» یا
  `POST /api/system/retention/run` (با `dry_run` برای بررسی).

## ۱۲. بازبینی کامل، پایداری و بهینه‌سازی

در یک بازبینی کامل کد (بک‌اند و رابط کاربری) موارد زیر اصلاح/بهینه شد. همه اعداد اندازه‌گیری
شده روی همین ماشین (GTX 1650، ویندوز، SQLite) هستند.

### باگ‌های واقعی که اصلاح شدند

1. **انحراف ۳:۳۰ ساعته در آمار «امروز».** `local_day_bounds()` زمان‌های آگاه از منطقه زمانی
   تهران را برمی‌گرداند، اما SQLite فقط «ساعت دیواری» را ذخیره می‌کند و `tzinfo` را نادیده
   می‌گیرد؛ نتیجه این بود که فیلترهای «امروز»/نمودار ساعتی ۳ ساعت و ۳۰ دقیقه جابه‌جا می‌شدند.
   اکنون مرزها به UTC برگردانده می‌شوند (تست رگرسیون اضافه شد).
2. **نادیده‌گرفتن منطقه زمانی در برنامه هشدارها.** خط لوله تشخیص، زمان محلی را با مقدار
   ثابت `Asia/Tehran` حساب می‌کرد؛ اکنون از `CAMERASMART_TIMEZONE` استفاده می‌کند.
3. **عدم کوچک‌سازی تصویر زنده.** `live_max_width=1280` برای دوربین ۱۹۲۰ پیکسلی هیچ اثری
   نداشت (باقی‌مانده تقسیم = ۱). اکنون گام نمونه‌برداری به بالا رُند می‌شود (۱۹۲۰ → ۹۶۰).
4. **دو دیکودر هم‌زمان برای یک دوربین.** اگر `stop()` در مهلت خود رشتهٔ خواندن را تمام
   نمی‌کرد، `start()` می‌توانست رشتهٔ دوم را روی همان دوربین اجرا کند (تشخیص و ثبت تکراری).
   اکنون رشتهٔ نیمه‌تمام نگه داشته می‌شود و تا پایان آن، راه‌اندازی مجدد انجام نمی‌شود.
5. **نشتی شمارندهٔ مرجع مدل.** هر `reload`/حذف دوربین یک مرجع اضافه می‌کرد و شمارندهٔ
   `registry` هرگز به صفر نمی‌رسید؛ اکنون هنگام خاموش‌کردن تشخیص یا حذف دوربین، مدل آزاد
   می‌شود و در تعویض مدل، مدل قبلی پس از جایگزینی برگردانده می‌شود.
6. **رشد بی‌مرز جدول نقشه حرارتی.** سلول‌های نقشه حرارتی هرگز پاک نمی‌شدند و درخواست
   `GET /api/stats/heatmap/{id}` بدون فیلتر روز، همهٔ سطرها را می‌خواند. اکنون جمع‌زدن در
   خود SQL انجام می‌شود و پاک‌سازی نگه‌داری، سلول‌های قدیمی را هم حذف می‌کند.
7. **پارامتر بی‌اثر `days`** در `GET /api/stats/overview` (رابط کاربری آن را می‌فرستاد ولی
   نادیده گرفته می‌شد) اکنون بازهٔ نمودار روزانه را تعیین می‌کند.
8. **حذف دوره‌ای معیارهای سلامت در هر ۱۰ ثانیه** (یک نوشتن بی‌دلیل) — اکنون حداکثر ساعتی یک‌بار.

### بهینه‌سازی‌های اندازه‌گیری‌شده

| مورد | قبل | بعد |
|---|---|---|
| تولید JPEG زنده برای هر دوربین بی‌تماشاگر | ~۸.۹ms/فریم (۱۸٪ یک هسته در ۲۰fps) | صفر (فقط وقتی مرورگر تماشا می‌کند) |
| تصویر زندهٔ دوربین ۱۹۲۰ پیکسلی با `live_max_width=1280` | بدون کوچک‌سازی (~۱۵ms/فریم) | ۹۶۰×۵۴۰ (~۲.۵ms/فریم) |
| نوشتن هر نتیجهٔ تشخیص در پایگاه داده | ~۶.۱ms (اتصال + PRAGMA + commit) | ~۲.۴ms (دسته‌ای در یک تراکنش) |
| ذخیرهٔ تصویر ۱۰۸۰p شیء (`optimize=True`) | ~۲۲.۵ms | ~۹.۵ms (حجم ~۷٪ بیشتر) |
| ترسیم/کدگذاری لایهٔ زندهٔ MJPEG | داخل حلقهٔ رویداد (توقف API) | در رشتهٔ کارگر (API آزاد) |

- رویکرد «تصویر زنده فقط هنگام تماشا» به‌صورت سازگار پیاده شد: دکمهٔ snapshot همچنان
  تصویر می‌دهد (کدگذاری درخواستی) و تایل‌های زندهٔ داشبورد/صفحهٔ دوربین با اتصال MJPEG،
  پخش را فعال می‌کنند.
- `CAMERASMART_DEBUG=true` دیگر به‌تنهایی تمام دستورهای SQL را چاپ نمی‌کند؛ برای آن
  `CAMERASMART_SQL_ECHO=true` لازم است (لاگ‌ها همچنان چرخشی و محدود به ۵×۱۰ مگابایت هستند).
- فایل نمونهٔ `backend\.env.example` بازنویسی شد (کلیدهای جدید `SQL_ECHO`, `RETENTION_AUTO_RUN`,
  `RETENTION_INTERVAL_HOURS`).
- رشتهٔ نگه‌داری خودکار در زمان راه‌اندازی سرور اجرا می‌شود و در خاموش‌شدن به‌درستی لغو می‌شود.

۹. **برنامهٔ هشدار در ناحیهٔ تودرتو کار نمی‌کرد.** فقط *نخستین* ناحیهٔ دربرگیرندهٔ شیء در نظر
   گرفته می‌شد؛ اگر یک ناحیهٔ عمومی (region) دور کل کادر و یک ناحیهٔ هشدار داخل آن بود،
   هشدار هیچ‌وقت فعال نمی‌شد. اکنون همهٔ ناحیه‌های دربرگیرنده بررسی می‌شوند (تست رگرسیون).
۱۰. **«database is locked» و از دست رفتن آمار نقشه حرارتی.** زیر حالت WAL، یک تراکنش
    خواندن‌وسپس‌نوشتن اگر در فاصلهٔ بین آن‌ها نویسندهٔ دیگری commit کند، بلافاصله با
    `SQLITE_BUSY_SNAPSHOT` شکست می‌خورد؛ و بدتر: بافر نقشه حرارتی پیش از نوشتن خالی می‌شد،
    پس آن آمار برای همیشه از دست می‌رفت. اکنون به‌روزرسانی هر سلول یک دستور اتمیک
    `INSERT .. ON CONFLICT DO UPDATE` است، بافر فقط پس از موفقیت تخیله می‌شود، نویسنده‌های
    پس‌زمینه با یک قفل مشترک هماهنگ می‌شوند و نوشتن نتایج تشخیص تا ۳ بار تلاش مجدد دارد.
۱۱. **فریز شدن API هنگام بارگذاری مدل.** ساخت مدل (import torch، خواندن وزن‌ها و در
    اولین اجرا دانلود آنها) داخل حلقهٔ رویداد انجام می‌شد و کل API و WebSocket را متوقف
    می‌کرد. اکنون روی رشتهٔ کارگر انجام می‌شود: در آزمون، ساخت دوربین با تشخیص فعال ۱۷
    ثانیه طول کشید ولی پاسخ `/api/system/ping` در همان مدت ~۳ میلی‌ثانیه بود.
۱۲. **باقی‌ماندن تصاویر دوربین حذف‌شده.** با حذف دوربین، سطرهای پایگاه داده حذف می‌شدند
    ولی فایل‌ها روی دیسک می‌ماندند (و نگه‌داری هم دیگر سراغشان نمی‌رفت). اکنون پوشهٔ همان
    دوربین هم پاک می‌شود (آزمون: ۱۲۳ فایل → ۰).
۱۳. **پاک‌سازی معیارهای سلامت و سلول‌های نقشه حرارتی** به نگه‌داری خودکار اضافه شد
    (پیش‌تر جدول نقشه حرارتی هرگز کوچک نمی‌شد) و حذف دوره‌ای سلامت از هر ۱۰ ثانیه به
    حداکثر ساعتی یک‌بار کاهش یافت.
۱۴. **آرام‌کردن لاگ‌های پرحجم:** `aiosqlite` دیگر هر دستور را در حالت DEBUG چاپ نمی‌کند
    (برای دیدن SQL از `CAMERASMART_SQL_ECHO=true` استفاده کنید).

### صحت‌سنجی

- تست‌های بک‌اند: **۳۰۰ تست موفق، ۱ تست skip (سالم)، ۰ خطا** (`pytest`؛ ۱۲ تست رگرسیون
  جدید برای همین اصلاحات).
- رابط کاربری: `tsc --noEmit` بدون خطا و `vite build` موفق (بدون تغییر در کد رابط).
- آزمون یکپارچگی درون‌فرآیندی با استریم واقعی فایل (`ffmpeg`) + خط لولهٔ واقعی: پیگیری
  ~۴.۶ فریم/ثانیه، ثبت ۲ مسیر (track)، رویدادهای ورود/خروج/عبور از خط، ۶ تصویر ذخیره‌شده
  (کامل+برش+بندانگشتی)، ۱ هشدار، سلول‌های نقشه حرارتی و معیارهای سلامت؛ حالت بی‌تماشاگر
  هیچ JPEG تولید نکرد و با بازکردن پخش زنده، کدگذاری از سر گرفته شد.
- آزمون HTTP روی پورت `۸۹۹۸` با پخش زندهٔ واقعی: ۱۰۸ فریم MJPEG در یک اتصال،
  `/snapshot` با `image/jpeg`، گالری با مسیر تصویر کامل و برش (سرو از `/media`)،
  نقشه حرارتی با ۱۴۲۲ شمارش، نمای کلی با ۷ باکت روزانه (یعنی پارامتر `days` کار می‌کند)،
  فید WebSocket با پیام‌های `detection` و `event`، و مدیریت GPU با اعداد واقعی.
- استنتاج واقعی RF-DETR: ۵۲ مسیر ثبت‌شده، ۹۸ رویداد، ۱۱۴ تصویر ذخیره‌شده و جهت‌های
  واقعی حرکت (`stationary/down/up/right/down-left/left`) روی یک ویدیوی ساخته‌شده از تصویر
  واقعی؛ بار GPU ~۷۰٪ و VRAM ~۴۸۰ مگابایت.
- آنچه هنوز آزمایش نشده: اتصال به یک دوربین RTSP واقعی روی شبکه (در این محیط در دسترس
  نبود)؛ همهٔ مسیرهای استریم با ورودی فایل و پروکسی‌های مطابق آزمون تست شده‌اند.

## ۱۳. دور دوم: تقسیم کد، پایداری مانیتورینگ GPU و توقف درخواست‌های بی‌نتیجه

### باگ‌های واقعی که اصلاح شدند

1. **خطای ۵۰۰ روی هر پرس‌وجوی `/api/system/gpu`.** در فرایند سرور (پس از آنکه torch بافت
   CUDA را می‌سازد) پرس‌وجوی `nvmlDeviceGetUtilizationRates` متناوباً `NVMLError_Unknown`
   می‌داد. چون هیچ محافظی نبود، کل endpoint با ۵۰۰ پاسخ می‌داد و پنل GPU در رابط کاربری هر
   چند ثانیه یک خطا می‌گرفت (در لاگ سرور ده‌ها اثر خطا). اکنون هر فراخوانی NVML جداگانه
   محافظت می‌شود؛ اگر داده‌ای که داشبورد به آن تکیه دارد خوانده نشود، به‌طور خودکار به
   `nvidia-smi` برمی‌گردد (نتیجهٔ زیرفرایند ۵ ثانیه کش می‌شود چون اجرای آن گران است) و این
   endpoint هرگز خطا برنمی‌گرداند (`available: false`). خواندن NVML/nvidia-smi نیز با
   `asyncio.to_thread` از حلقهٔ رویداد خارج شد تا به تأخیر استریم زنده اضافه نکند.
2. **پرس‌وجوی ابدی روی منابع ۴۰۴.** صفحهٔ جزئیات دوربینی که وجود ندارد، هر ۱ ثانیه
   `/api/cameras/{id}/status` را با خطای ۴۰۴ تکرار می‌کرد و کنسول مرورگر را پر می‌کرد.
   اکنون خطاهای ۴xx هرگز دوباره تلاش نمی‌شوند و پرس‌وجوی منبعی که مقدار ۴xx می‌دهد متوقف
   می‌شود؛ صفحه به‌درستی حالت «دوربین یافت نشد» را نشان می‌دهد.

### بهینه‌سازی اندازه‌گیری‌شده: تقسیم کد در سطح مسیر

پیش‌تر همهٔ صفحه‌ها به‌صورت ایستا وارد می‌شدند و یک بستهٔ واحد ۹۶۰ کیلوبایتی می‌ساختند. اکنون
هر مسیر جداگانه بارگذاری می‌شود (`React.lazy` با مرز `Suspense` در پوستهٔ برنامه، پس نوار
کناری و فید زنده در حین بارگذاری نمای صفحه حذف نمی‌شوند):

| بستهٔ ورودی | قبل | بعد |
| --- | --- | --- |
| حجم خام | ۹۶۰.۸۵ کیلوبایت | ۲۹۱.۸۴ کیلوبایت |
| حجم gzip | ۲۷۵ کیلوبایت | ۹۳.۸۷ کیلوبایت |

`recharts` (۳۴۴ کیلوبایت) اکنون فقط هنگام باز کردن صفحه‌های نموداردار (داشبورد/آمار/جزئیات
دوربین) درخواست می‌شود؛ تأیید شد که در بازدید از `/cameras` هیچ بستهٔ نموداری بارگذاری نمی‌شود.

### آزمون‌ها و تأیید

- بک‌اند: **۳۰۷ آزمون موفق، ۱ رد‌شده، ۰ ناموفق** (پیش‌تر ۳۰۱) — ۶ آزمون جدید در
  `tests/test_gpu.py` که شکست NVML و بازگشت به `nvidia-smi` را قفل می‌کنند.
- تأیید زنده روی سخت‌افزار واقعی: شکست NVML در فرایند سرور بازتولید و مهار شد؛ ۱۲ پرس‌وجوی
  پیاپی `/api/system/gpu` همه ۲۰۰ با دما/توان واقعی (جابه‌جایی خودکار بین `pynvml` و
  `nvidia-smi`) و صفر اثر خطا در لاگ؛ پیش‌تر هر پرس‌وجو یک خطای ۵۰۰ بود.
- رابط کاربری: `tsc --noEmit` و `vite build` موفق؛ همهٔ مسیرها در مرورگر بارگذاری و رندر
  شدند و پرس‌وجوی ۴۰۴ پس از بارگذاری کاملاً متوقف شد (در کل ۲ درخواست، هیچ‌کدام پس از ۹ ثانیه).

## ۱۴. دور سوم: امنیت ورود، اصلاح باگ‌های مانده و قفل نسخه‌ها

### ۱۴.۱. ورود با رمز ادمین (تک‌کاربره)

پیش‌تر هر کسی که به شبکهٔ محلی دسترسی داشت می‌توانست استریم زنده، تصاویر و تنظیمات
(شامل حذف دوربین) را ببیند و تغییر دهد. اکنون:

- در **اولین اجرا** صفحهٔ تعیین رمز باز می‌شود و رمز **دو بار** گرفته می‌شود؛ از آن پس همان رمز
  برای ورود کافی است. کاربر یا نقش دیگری تعریف نمی‌شود.
- رمز با `hashlib.scrypt` (نمک تصادفی، پارامترهای استاندارد) هش می‌شود؛ متن رمز هرگز ذخیره
  یا لاگ نمی‌شود. پیاده‌سازی فقط از کتابخانهٔ استاندارد پایتون است (وابستگی جدیدی اضافه نشد).
- نشست: کوکی امضاشده با HMAC-SHA256 (`camerasmart_session`، `HttpOnly`، `SameSite=Lax`،
  پیش‌فرض ۱۲ ساعت). تغییر رمز، کلید امضا را می‌چرخاند و همهٔ نشست‌های دیگر را باطل می‌کند.
- قفل تلاش ناموفق: پس از ۵ تلاش، ورود ۶۰ ثانیه قفل می‌شود (قابل تنظیم با
  `CAMERASMART_AUTH_MAX_ATTEMPTS` و `CAMERASMART_AUTH_LOCKOUT_SECONDS`).
- محافظت در یک لایه (`AdminAuthMiddleware`) روی **همهٔ** `/api/*` و `/media/*` اعمال می‌شود؛
  فقط `ping` و مسیرهای `auth` عمومی‌اند. فایل‌های ایستای رابط کاربری عمومی می‌مانند تا صفحهٔ
  ورود بتواند بارگذاری شود. WebSocket پیش از `accept` کوکی و Origin را بررسی می‌کند (کد ۱۰۰۸).
- درخواست‌های تغییردهنده از Origin بیگانه با ۴۰۳ رد می‌شوند (CORS با `*` دیگر با credentials
  ترکیب نمی‌شود) و هدرهای امنیتی پایه (`nosniff`، `SAMEORIGIN`، `Referrer-Policy`) اضافه شد.
- نام کاربری/رمز داخل آدرس RTSP در همهٔ پاسخ‌ها ماسک می‌شود (`rtsp://***@host/path`)؛ در ویرایش،
  اگر همان مقدار ماسک‌شده برگردد، آدرس اصلی ذخیره‌شده دست‌نخورده می‌ماند.
- رابط کاربری: صفحهٔ ورود/راه‌اندازی، دروازهٔ احراز هویت (تا قبل از ورود هیچ صفحه‌ای بارگذاری
  نمی‌شود)، خروج در نوار بالا، و بازگشت خودکار به صفحهٔ ورود با هر پاسخ ۴۰۱.

### ۱۴.۲. باگ‌هایی که در این دور اصلاح شدند

| مشکل | اصلاح |
|---|---|
| هر بار اتصال مجدد، `ffprobe` از نو اجرا می‌شد (تا ۱۵ ثانیه تأخیر) | نتیجهٔ probe برای هر URL یک‌بار کش می‌شود |
| کدگذاری JPEG روی رشتهٔ ویدیو انجام می‌شد و فریم بعدی را عقب می‌انداخت | نوشتن snapshot به worker پس‌زمینه منتقل شد |
| پاک‌سازی نگه‌داری همهٔ ردیف‌های قدیمی را در حافظه بار می‌کرد | حذف دسته‌ای (۵۰۰ ردیف در هر گام) و شمارش با `COUNT` |
| نتایج صف‌شدهٔ دوربین حذف‌شده، تاریخچهٔ آن را بازمی‌ساختند | بررسی وجود دوربین پیش از نوشتن (با کش کوتاه) |
| `alerts_enabled`, `alert_sound_default`, `record_objects` در UI بودند ولی خوانده نمی‌شدند | هر سه اکنون رفتار واقعی دارند (خاموش‌کردن هشدارها، صدای پیش‌فرض ناحیهٔ جدید، ذخیرهٔ تصویر اشیا) |
| پارامترهای `/api/search/point` نادیده گرفته می‌شدند و کد مرده داشت | پارامترها کامل به کوئری می‌رسند و تابع بی‌استفاده حذف شد |
| `backend/test.py` اسکریپت سرگردان و بی‌مصرف بود | حذف شد |
| یک خطای رندر، کل صفحه را سفید می‌کرد | `ErrorBoundary` با پیام و دکمهٔ بارگذاری مجدد |

### ۱۴.۳. نسخه‌ها

- پایتون: ماتریس تأییدشده در `backend/constraints.txt` پین شد و `numpy` در همهٔ فایل‌ها به
  `<2.0` یکسان‌سازی شد (پیش‌تر `requirements-core` اجازهٔ numpy 2 می‌داد که با torch 2.5.1
  ناسازگار است). ارتقای torch عمداً انجام نشد: ~۳ گیگابایت دانلود و ریسک شکستن rfdetr دارد و
  نسخهٔ فعلی روی همین سخت‌افزار با استریم زنده و کل تست‌ها تأیید شده است.
- npm: همهٔ بسته‌ها به آخرین نسخهٔ سازگار به‌روز و **پین** شدند؛ `npm outdated` خالی است و
  `npm run typecheck` و `npm run build` موفق‌اند.

### ۱۴.۴. صحت‌سنجی این دور

- بک‌اند: **۳۱۸ آزمون، ۰ ناموفق** (۱ رد‌شده) — شامل ۱۱ آزمون جدید امنیتی/رگرسیون
  (`tests/test_auth.py` و نگاشت برچسب در `tests/test_detector.py`).
- آزمون سرتاسری روی نسخهٔ اجرایی (پایگاه دادهٔ موقت، پورت ۸۰۱۱): وضعیت اولیه «تنظیم‌نشده» →
  API محافظت‌شده ۴۰۱ → `setup` با کوکی → ۲۰۰ → ساخت دوربین → استریم `online` با ۴٫۹۹ فریم و
  بیت‌ریت ۱۴۵ kbps → MJPEG پنج فریم → snapshot ۲۰۰ → خروج ۴۰۱ → رمز اشتباه ۴۰۱ → رمز درست ۲۰۰؛
  بدون هیچ خطا/exception در لاگ سرور.
- رابط کاربری: `tsc --noEmit`، `vite build` و `npm install` موفق؛ صفحهٔ ورود در مرورگر باز و
  بررسی شد (تکمیل فرم و ورود واقعی با رمز، در آزمون HTTP بالا پوشش داده شد).

### ۱۴.۵. باقی‌مانده (عمداً به مرحلهٔ بعد)

- **ضبط و بازپخش ویدیو** (مورد ۲۲ فهرست): نیازمند طراحی ذخیره‌سازی قطعه‌ای، ایندکس زمانی و
  پخش‌کننده است و به‌تنهایی یک قابلیت کامل است؛ در این دور انجام نشد.
- ارتقای torch به CUDA جدیدتر (به دلیل بالا) و برچسب «تخمینی» برای بیت‌ریت وقتی probe در
  دسترس نیست (اکنون مقدار ۰ نمایش داده می‌شود).

### ۱۵.۲. اصلاحات رابط کاربری

| مشکل | اصلاح |

### ۱۵.۳. بررسی چشمی

صفحه‌ها در مرورگر واقعی (نمونهٔ موقت با پایگاه دادهٔ جدا، پورت ۸۰۱۲) باز و بررسی شدند:
صفحهٔ ورود، داشبورد زنده (تشخیص انسان/اتوبوس روی کلیپ آزمایشی)، صفحهٔ دوربین‌ها با تصویر
لایه‌گذاری‌شده، تنظیمات (شامل کارت «امنیت و رمز ادمین»)، کشوی منوی موبایل و پوستهٔ روشن.
اسکرین‌شات‌ها در `ui-shots/` (خارج از گیت) هستند.

- بک‌اند: **۳۱۸ آزمون، ۰ ناموفق**؛ `tsc --noEmit` و `vite build` موفق.
- این بررسی روی یک نمونهٔ موقت انجام شد تا رمز ادمین و دادهٔ واقعی شما دست‌نخورده بماند.

## ۱۶. دور پنجم: بهینه‌سازی مصرف منابع سخت‌افزاری

اندازه‌گیری‌ها روی همین سیستم (Core i5‑12450H، ۸ هسته؛ GeForce GTX 1650 با ۴GB) و روی
فریم ۱۰۸۰p انجام شد؛ میانهٔ ۱۰ اجرا.

| کار | قبل | بعد |
|---|---|---|
| `MotionDetector.update` روی ۱۰۸۰p | ۲۱٫۹ ms | **۱٫۹ ms** (downscale قبل از خاکستری‌سازی) |
| گپ فریم‌ها با استنتاج ۱۰۰ms (p95) | ۱۱۱ ms | **۶۴ ms** (تشخیص از رشتهٔ دیکد جدا شد) |

### ۱۶.۱. تغییرات رفتاری/ساختاری

- **حرکت ارزان شد:** در `motion._gray_small` اول stride زده می‌شود و بعد خاکستری می‌شود؛
  قبلاً ۱۶/۱۵ محاسبهٔ گران دور ریخته می‌شد. حرکت از قبل با کادنس تشخیص (۵fps) اجرا
  می‌شد، پس سود آن ۱۰ برابر شدن ارزانی هر فراخوانی است، نه کاهش تعداد فراخوانی.
- **تشخیص روی رشتهٔ جدا:** هر دوربین یک `detect-<id>` دارد با صف «آخرین فریم برنده»
  (maxsize=1). استنتاج دیگر خواندن فریم را متوقف نمی‌کند؛ با چهار دوربین و مدل مشترک،
  هیچ دوربینی پشت قفل مدل کور نمی‌ماند.
- **انتخاب خودکار مدل:** برای دوربین جدید، سنگین‌ترین مدلی انتخاب می‌شود که با ۱۵٪
  هد‌روم پاسخ بدهد (۱ دوربین → base، ۲ → small، ۳ و بیشتر → nano). `CAMERASMART_AUTO_MODEL_SELECTION=false`
  این رفتار را خاموش می‌کند.
- **بودجهٔ تشخیص در UI:** `/api/system/runtime` مقدار `manager.detection_budget` را برمی‌گرداند
  و داشبورد در صورت منفی‌شدن بودجه (تقاضا > ظرفیت مدل) هشدار و مدل پیشنهادی نشان می‌دهد.
- **نمای زنده سبک‌تر:** `CAMERASMART_DEFAULT_STREAM_FPS=12` (از ۲۰)،
  `CAMERASMART_LIVE_MAX_WIDTH=960` (از ۱۲۸۰)، سقف `CAMERASMART_LIVE_MAX_FPS=20` و
  کاشی‌های داشبورد حداکثر ۱۲fps درخواست می‌کنند.
- **تصویر شاهد محدود شد:** `CAMERASMART_SNAPSHOT_MAX_WIDTH=1280` (۰ = اندازهٔ اصلی)؛
  کادرها نرمال‌شده‌اند، پس crop و bbox دقیق می‌مانند و حجم دیسک هم کم می‌شود.
- **امتیاز کیفیت فقط وقتی لازم است:** `evaluate_frame` تنها وقتی صدا زده می‌شود که تصمیم
  ثبت تصویر به آن وابسته باشد؛ در بقیهٔ فریم‌ها آخرین امتیاز شیء استفاده می‌شود.
- **پایگاه داده:** `CAMERASMART_DATABASE_POOL_SIZE=2` به‌همراه حداکثر ۶ اتصال سرریز
  (۸ اتصال)؛ ۰ = `NullPool`. تست‌ها به‌خاطر ساخت event loop در هر تست روی `NullPool`
  می‌مانند (`conftest.py`).
- **پایان‌گرفتن اشغال اتصال:** نمای زنده (`/live`) تا وقتی صفحه باز است طول می‌کشد و
  Dependency آن فقط پس از پایان استریم بسته می‌شود؛ برای همین نشست را قبل از برگرداندن
  `StreamingResponse` (و پیش از کدگذاری JPEG در `/snapshot`) می‌بندیم. `reload_camera` هم
  نشست را قبل از بارگذاری مدل می‌بندد. پیش از این، دو نمای زندهٔ باز کل استخر را اشغال
  می‌کردند و ذخیرهٔ دوربین با `QueuePool limit ... connection timed out` شکست می‌خورد.

### ۱۶.۲. چیزهایی که عمداً انجام نشد

- **FP16:** `model.inference(dtype=torch.float16)` روی GTX 1650 از ۱۰۶ms به ۳۸۲ms بدتر شد
  (این کارت هستهٔ Tensor ندارد). روی RTX ارزش دارد، ولی چون سود آن به سخت‌افزار وابسته است
  پیش‌فرض نشد.
- **batch inference:** مدل rfdetr برای batch=1 کامپایل شده و `predict([f, f])` خطا می‌دهد؛
  بدون بازسازی مدل ممکن نیست.
- **دیکد سخت‌افزاری:** `-hwaccel d3d11va` بدون `hwdownload` صفر فریم می‌دهد و دیکد نرم‌افزاری
  فقط ۳٫۵ms/فریم است (۷٪ هسته)؛ برای ۴K یا ۸+ دوربین باید جداگانه بررسی شود.

### ۱۶.۳. آزمون‌ها

- بک‌اند: **۳۱۸ آزمون، ۰ ناموفق، ۱ ردشده**.
- `npm run typecheck` و `npm run build` موفق.
- بررسی رفتار رشتهٔ تشخیص با یک reader ساختگی: `detection_fps ≈ ۴` روی هدف ۵، دو رشتهٔ
  مجزا، و توقف تمیز (`stop` هر دو رشته را می‌بندد).
- سقف عرض تصویر شاهد: فریم ۱۹۲۰×۱۰۸۰ → فایل ۱۲۸۰×۷۲۰، crop و ابعاد گزارش‌شده سازگار.

## ۱۷. دور ششم: زمان‌بند مرکزی استنتاج، صف‌های محدود و مانیتورینگ کامل

این دور با یک آزمون فشار واقعی روی همان سیستم (Core i5‑12450H، ۱۲ رشته؛ GTX 1650 ۴GB)
انجام و اندازه‌گیری شد؛ نه با حدس. سه دوربین/دوربین‌های ۴ و ۸ گانه روی یک منبع RTSP مشترک
(MediaMTX + ffmpeg، ۱۲۸۰×۷۲۰، ۲۰fps) اجرا شدند و اسکریپت `scripts/soak_cameras.py`
هر ۱۰ ثانیه `/api/system/runtime` را نمونه‌برداری کرد.

### ۱۷.۱. مشکل واقعی چه بود

قبلاً هر دوربین یک رشتهٔ `detect-<id>` داشت که روی `RFDetrDetector._lock` می‌ایستاد.
نتیجه: صف نامرئی جلوی قفل، بدون سنجش و بدون فشار معکوس (backpressure). در همین بررسی
سه ایراد دیگر هم پیدا شد که هیچ‌کدام از لاگ‌های معمولی دیده نمی‌شدند:

- **صف snapshot بی‌حد بود:** `ThreadPoolExecutor` صف نامحدود دارد؛ با ۸ دوربین پرتحرک
  فریم‌های کدشده در RAM جمع می‌شدند و فقط سیستم کندتر می‌شد.
- **ا فراخوانی بازگشتی بعد از قطع ناشر:** MediaMTX برای مسیر بدون ناشر، نشست RTSP را
  می‌پذیرد و فوراً می‌بندد. دوربین هر ~۱ ثانیه دوباره وصل می‌شد — **۲۴۶ اتصال در ۵ دقیقه**
  برای هر دوربین (اندازه‌گیری‌شده) با CPU و لاگ بی‌فایده.
- **مسابقهٔ حذف دوربین با ذخیره‌سازی:** حذف دوربین در حالی که نتایجش در صف بود،
  `FOREIGN KEY constraint failed` می‌داد و در لاگ به‌شکل stack trace دیده می‌شد.

### ۱۷.۲. معماری جدید پردازش

::

    هر دوربین                        زمان‌بند مرکزی                مصرف‌کننده‌ها
    ─────────────────────────────    ────────────────────────    ───────────────────────────
    ffmpeg decode thread             یک رشتهٔ dispatcher          asyncio persister
      ├─ فریم ──> MJPEG (اگر بیننده)   slot[دوربین] (ظرفیت ۱)        └─ SQLite (batch)
      ├─ فریم ──> slot دوربین   ───>  round-robin  ──> pipeline    snapshot writer (N worker،
      │                                (حرکت → تشخیص → ردیابی)             صف محدود، JPEG + دیسک)
      └─ health/telemetry

- `app/services/inference.py` — **`InferenceScheduler`**: یک رشته، یک مدل، یک صف یک‌فریمی
  برای هر دوربین (فریم جدید جای فریم منتظر را می‌گیرد)، پیمایش round-robin و شمارش
  `processed/dropped/errors/wait_ms/inference_ms` به‌ازای هر دوربین. استنتاج دیگر پشت
  هیچ قفل مشترکی پنهان نمی‌شود؛ ترتیب اجرا منصفانه و قابل اندازه‌گیری است.
  - باگ ظریف که تست پیدا کرد: دوربینی که در حین اجرا فریم دوم را می‌فرستاد، چون «صف
    خالی نبود»، دوباره به لیست آماده اضافه نمی‌شد و فریم دومش هرگز اجرا نمی‌شد؛ اکنون
    صف هر دوربین بعد از برداشتن هر فریم دوباره به انتهای نوبت اضافه می‌شود.
- **یک بار بارگذاری مدل:** `DetectorRegistry` مثل قبل مدل مشترک را نگه می‌دارد؛ زمان‌بند
  فقط همان نمونه را صدا می‌زند.
- **ظرفیت واقعی GPU:** پس از بارگذاری، مدل سه فریم آزمایشی اجرا می‌شود، `latency_ms`
  ثبت و `models_registry.note_measured_latency` جدول ظرفیت را با ضریب دستگاه مقیاس
  می‌کند. بودجهٔ تشخیص و «مدل پیشنهادی» حالا بر اساس همین دستگاه است، نه جدول GTX 1650.
- **FP16/CUDA خودکار:** `wants_half_precision()` روی سخت‌افزار تصمیم می‌گیرد: کارت با
  Tensor Core (RTX/A-series، capability ≥ ۷) → FP16؛ GTX 16xx (Turing بدون Tensor Core)
  → FP32. روی A2000 انتظار ~۲ برابر است (اینجا کارت ۱۶۵۰ است، پس اندازه‌گیری نشد)،
  روی همین کارت FP16 اندازه‌گیری شد ۲۶۴ms در برابر ۶۴ms برای FP32 و درست انتخاب نشد.
  به‌علاوه `cudnn.benchmark` و TF32 برای کارت‌های Ampere به بعد روشن می‌شوند.
- **CPU-only:** بدون GPU هم همان مسیر کار می‌کند؛ `torch.set_num_threads(cpu-1)` تا
  ffmpeg‌ها هستهٔ آزاد داشته باشند.

> نکتهٔ حافظه: `model.inference(compile=True)` نسخهٔ trace شده را کنار مدل اصلی نگه
> می‌دارد (روی این سیستم ~۱GB RAM اضافه، اندازه‌گیری‌شده). در ازایش هر فریم از ۱۰۶ms
> جدول به ۶۴ms رسید. اگر RAM کم است، `CAMERASMART_OPTIMIZE_FOR_INFERENCE=false`.

### ۱۷.۳. پردازش تصاویر

- **رزولوشن استنتاج جدا از نمایش:** `CAMERASMART_DETECTION_MAX_WIDTH` (یا فیلد «عرض ورودی
  مدل» در تنظیمات). فریم فقط برای مدل کوچک می‌شود؛ چون RF-DETR مختصات را نسبت به تصویری
  که گرفته نرمال می‌کند، کادرها روی فریم اصلی معتبر می‌مانند (تست دارد).
- **حذف کار تکراری:** لیست‌های ناحیه (process/ignore/line) یک بار ساخته و کش می‌شوند
  (قبلاً برای هر تشخیص و هر شیء از نو ساخته می‌شدند)؛ `box_center` بلااستفاده حذف شد.
- **بافر قابل‌نوشتن:** فریم پیش از استنتاج با `ascontiguousarray` تضمین می‌شود
  (`torch.from_numpy` روی آرایهٔ read-only هشدار می‌داد).
- **ردیابی:** در تخمین حرکت دوربین، resize قبل از `cvtColor` انجام می‌شود (تبدیل رنگ روی
  ۱۰۸۰p گران‌تر بود).

### ۱۷.۴. ذخیره‌سازی

- `SnapshotWriter` در `app/services/persistence.py`: صف **محدود** + N رشتهٔ کارگر،
  قابل تنظیم (`CAMERASMART_SNAPSHOT_WORKERS`, `..._SNAPSHOT_QUEUE_SIZE`) و قابل تغییر در
  زمان اجرا (`resize`) بدون از دست دادن کار صف. اگر دیسک عقب بماند، snapshot جدید رد
  می‌شود و **شمارش** می‌شود؛ متادیتای رویداد همچنان ذخیره می‌شود.
- `CAMERASMART_PERSIST_BATCH_MAX` تعداد نتیجه در هر تراکنش SQLite است.
- حذف دوربین در حین ذخیره‌سازی دیگر stack trace تولید نمی‌کند: `IntegrityError` باعث
  بازبینی وجود دوربین و حذف آرام آن دسته می‌شود (تست دارد).
- خطاهای نوشتن snapshot و persist در تلمتری شمرده می‌شوند (`errors`, `last_error`).

### ۱۷.۵. استریم و اتصال مجدد

- بازگشت به عقب (backoff) فقط با **باز شدن موفق** نشست ریست نمی‌شود؛ پس از یک نشست
  **بدون فریم** هم backoff اعمال می‌شود (۱،۲،۴،۸… تا ۳۰ ثانیه). اندازه‌گیری: قطع ناشر
  به مدت ۳۲ ثانیه = **۶** تلاش، در برابر **۲۴۶** تلاش در ۵ دقیقه قبل از اصلاح.
- توقف/حذف/ری‌لود: دوربین از زمان‌بند `unregister` می‌شود، فریم‌های منتظرش دور ریخته
  می‌شوند، ffmpeg بسته و snapshot‌های در جریان رها می‌شوند؛ سایر دوربین‌ها دست نمی‌خورند.
- RTSP و پردازش AI کاملاً مستقل‌اند: هر دوربین رشتهٔ دیکد خودش را دارد و استنتاج در
  زمان‌بند مرکزی اجرا می‌شود؛ کندی GPU خواندن فریم را متوقف نمی‌کند.

### ۱۷.۶. نمایش زنده (Frontend)

- کاشی که از دید خارج شود (IntersectionObserver) یا تب پنهان باشد، اتصال MJPEG را نگه
  نمی‌دارد؛ با بازگشت به دید دوباره وصل می‌شود.
- قطع استریم دیگر «قاب مرده» نیست: تلاش مجدد با backoff نمایی (۱٫۵s تا ۱۵s).
- نرخ نمایش کاشی‌ها از تنظیمات کنترل می‌شود (`gridLiveFps`، پیش‌فرض ۱۰fps و سقف نرخ
  خود دوربین) و روی همین مرورگر ذخیره می‌شود.
- Overlay و کادرها دست‌نخورده‌اند؛ نرخ نمایش مستقل از نرخ تشخیص است.

### ۱۷.۸. نتایج اندازه‌گیری (قبل/بعد، همین سیستم)

۴ دوربین، منبع ۷۲۰p/۲۰fps، مدل base، تشخیص ۵fps، ۱۵۰–۱۷۰ ثانیه:

| شاخص | قبل (HEAD) | بعد |
|---|---|---|
| تشخیص هر دوربین | ۲٫۵–۲٫۶ fps | **۲٫۷–۲٫۸ fps** |
| مجموع تشخیص | ۱۰٫۷ fps | **۱۱٫۱ fps** |
| صف/تأخیر استنتاج | نامعلوم (قفل، بدون سنجش) | wait ≈۹۰ms، هر دوربین یک فریم |
| فریم‌های جایگزین‌شده | شمرده نمی‌شد | ۹۲۵ (جدیدترین فریم همیشه برنده) |
| snapshot نوشته/رد/خطا | بدون شمارش، صف بی‌حد | ۸۹۳ / ۰ / ۰ |
| خطای ذخیره‌سازی | ۰ (ولی FK race داشت) | ۰ |
| RAM (رشد در اجرا) | — | +۴۰MB، VRAM ثابت ۱۰۷۸MB |

### ۱۸.۲. اصلاحات عملکردی و رفتاری

- **Encode زنده با نرخ بیننده:** قبلاً `?fps=2` فقط تحویل را کند می‌کرد و بک‌اند هنوز ۲۰ JPEG در ثانیه می‌ساخت. اکنون `mark_live_view(fps)` نرخ را به decoder می‌دهد و `_publish_frame` با همان فاصله encode می‌کند. اندازه‌گیری واقعی: ۸ ثانیه پخش با `?fps=2` ⇒ **۱۵ encode** (یعنی ~۲/ثانیه) به‌جای ~۱۶۰.
- **قاب مرده حذف شد:** کش JPEG تاریخ دارد؛ اگر decoder بیش از ۳ ثانیه فریمی نداده باشد، MJPEG به‌جای تکرار بی‌پایان آخرین تصویر، پلیس‌هولدر «no signal» می‌فرستد.
- **فریم در حال پرواز دوربین حذف‌شده:** `scheduler.submit` برای دوربین `unregister` شده `False` برمی‌گرداند و slot را زنده نمی‌کند (دیگر دوربین حذف‌شده در آمار و `pending` نمی‌ماند).
- **متریک‌های سلامت درست شدند:** اولین اتصال «reconnect» شمرده نمی‌شود؛ تلاش‌های ناموفق اتصال در `connect_failures` جدا می‌شوند و `dropped_frames` فقط خطای خواندن است؛ نرخ تشخیص در لحظهٔ **اجرا** اندازه‌گیری می‌شود (نه لحظهٔ ارسال به صف، که با صف شلوغ ترتیب را به‌هم می‌زد و ۰fps نشان می‌داد). شمارندهٔ `live_encoded` هم اضافه شد.
- **خاموشی بدون گم‌شدن شواهد:** `CameraManager.stop()` نویسندهٔ snapshot را هم می‌بندد (قبلاً رشته‌های daemon با صف پر کشته می‌شدند) و یک writer بسته‌شده دیگر کار نمی‌پذیرد.
- **Retention:** پاک‌سازی بزرگ قفل نوشتن مشترک را می‌گیرد (روی SQLite یک نویسنده) و فایل‌ها **بعد از commit** حذف می‌شوند، نه قبلش.
- **بارگذاری مدل بیرون از Event Loop:** `sync_from_db` مدل‌ها را در thread لود می‌کند و یک لود ناموفق ۶۰ ثانیه کش می‌شود تا هر درخواست بعدی دوباره ۱۰–۲۰ ثانیه فریز نکند.
- **تغییر Device/FP16:** پس از reload همهٔ دوربین‌ها `torch.cuda.empty_cache()` صدا زده می‌شود تا VRAM مدل قبلی روی کارت ۴GB نماند.
- **صف نتیجه بدون polling:** `_consume_loop` روی یک `asyncio.Event` می‌خوابد و decode thread آن را با `call_soon_threadsafe` بیدار می‌کند (قبلاً ۳۳ بیداری بی‌مورد در ثانیه + ۳۰ms تأخیر).
- **MJPEG بدون hop به ThreadPool:** خواندن کش JPEG در خودِ event loop انجام می‌شود (فقط overlay در thread می‌ماند) — قبلاً با ۸ کاشی ~۸۰ hop در ثانیه بود.
- **Middleware خالص ASGI:** `AdminAuthMiddleware` دیگر `BaseHTTPMiddleware` نیست؛ استریم‌های دقیقه‌ای MJPEG یک لایهٔ task group اضافه ندارند.
- **توقف فوری دوربین:** `stop()` لولهٔ reader را می‌بندد تا رشتهٔ دیکدِ گرفتار در socket read بلافاصله برگردد (قبلاً تا ۸ ثانیه معطل می‌ماند و ری‌استارت را قفل می‌کرد).
- **فرانت:** کاشی با تب پنهان (`visibilitychange`) استریم را قطع می‌کند و درخواست‌های API تایم‌اوت ۳۰ ثانیه‌ای دارند (قبلاً اسپینر بی‌پایان).
- ۹ ایمپورت بلااستفادهٔ قدیمی هم پاک شد؛ `ruff check --select F,E9` اکنون **All checks passed**.
